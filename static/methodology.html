How this agent is trained

A fixed pauper card pool, several decks, and one loop: play games against varied opponents, turn the outcome into a policy-gradient update, and periodically check the result against fixed benchmarks. Everything below is the real implementation, not a simplified model of it — expand any ▸ drill-down block for the exact mechanism.

Stage 1

Self-Play League Structure

Training runs as a league: a roster of decks that all improve together, playing each other and their own past selves. Three populations exist per league, and only one of them is the actual training target.

Primary League

e.g. main-league — the actual thing being trained
Live nets — one live.pt per deck, updated every PPO step
Archive — rolling window of 32 frozen historical snapshots per deck (PFSP opponent pool)
PFSP sampler — picks which deck, then live-vs-snapshot, weighted toward opponents this deck is currently losing to

Training League (twin)

same roster/mechanics, independent trajectory, frozen size
Fixed at 10,000 games/deck — never extended, even as the primary keeps training
Exists purely as a benchmark opponent pool — since it stops improving, a rising win rate against it isn't confounded by "everyone got better together"
Built only if the config sets create_training_league: true
both populations feed round-robin evaluation ↓ (see Validation)

One training session, step by step

  1. Load (or resume) every train deck's network and optimizer state from live.pt, plus its mulligan net with a separate optimizer.
  2. Per iteration, per train deck: sample an opponent (PFSP-weighted deck, then live-vs-snapshot), collect rollout games, run a PPO update on that deck's own buffer — and also update any other train deck whose buffer was generated as a live opponent in those same games ("salvaging").
  3. Every 8 iterations (or the session's last one), flush accumulated mulligan-decision transitions through one REINFORCE step per deck.
  4. When cumulative games cross the snapshot cadence, freeze a new snapshot per deck into the league pool, save live checkpoints + optimizer state + opponent stats, and update progress.json.
  5. Always re-save live checkpoints at session end.

A real run is many separate process invocations of this session, chained by the higher-level pipeline runner until a deck hits its configured total_games, with the full validation suite run after each chunk.

PFSP opponent weighting — weight vs. this deck's win rate against a candidate

weight = 0.1 + (1 − win_rate)^0.5. A never-played opponent starts at a neutral 0.5 win-rate prior. The 0.1 floor keeps even lopsided matchups in rotation instead of dropping to zero.

Archive & snapshot eviction
Each deck keeps at most 32 snapshots as PFSP opponents. When a new snapshot would overflow that window, the oldest one is moved (never deleted) into <deck>/archive/. Archived snapshots stay playable — the vs_history validation check pits a deck's current live net against its oldest still-active snapshot and, once one exists, its oldest archived one too.

Every deck owns its own encoder and trunk — nothing is shared across decks. That costs cross-deck transfer, but means one deck's representation never has to compromise for another's.

Per-token features (what each card contributes)
Static half — doesn't change turn to turn: mana cost pips, card type one-hot, base power/toughness, keyword multi-hot (scanned from the effect registry), mana-production features, spec-key multi-hot, pending-kind multi-hot, extra-flag multi-hot (artifact / basic / defender / indestructible / devoid), subtype multi-hot.

Dynamic half — current state: tapped, effective P/T, blocked / attacking / summoning-sick flags, aura attachment, targeted-by-mine / targeted-by-theirs, revealed-hand disposition bits, counter counts, zone one-hot, side flag.

Opponent's hand and both libraries are hidden by default — aggregate counts only via the scalar globals — except two narrow reveal cases (Mesmeric-Fiend-style effects, and scry/surveil/ponder/tuck "revealed" holding areas), which get real tokens.
Scalar globals (non-tokenized state)
Turn number, lands played this turn, mulligans taken (both seats), life totals, mana pools by color, phase one-hot, library sizes, opponent hand size, stack-targeting flags, on-the-play, opponent discard count. Concatenated with the "mine" summary before the trunk.
Why FiLM instead of just concatenating the opponent summary
A small conditioner MLP turns theirs_summary into per-layer (γ, β) pairs that rescale and shift each trunk layer's activations (γ·h + β), rather than appending it as extra input features. The opponent's board state gates how the trunk processes your own state, instead of just being one more thing concatenated in.
Why a GRU on top of an already-Markov board state
The encoded board is itself close to fully observable, but recent history still carries information the current snapshot doesn't — what mana got held up and passed, what was declined last turn. The GRU is fed the trunk output plus an embedding of the agent's own previous action, giving it that short-term memory. PPO updates replay whole episodes through it in order from a zero hidden state — see PPO Training.
Stage 3

Action Space

Actions come from one combined softmax, not two separate distributions — a fixed-table entry and a pointer-scored target can both be legal at the same decision, so they compete in a single masked distribution rather than being chosen in two stages.

Fixed table — menu-shaped

  • Play land / Cast a spell / Activate an ability
  • Forestcycle
  • Pass
  • Mana-payment choices
  • "Choose: X" / "Choose: X as color" resolution picks
  • Keep / Dispose, Decline, Abandon payment
  • Mulligan actions, "Done blocking"

fixed shape per deck, built once from its decklist

Pointer head — context-shaped

  • Attack, assign blocker
  • Choose target / opponent's permanent
  • Assign combat damage
  • Choose-any-target effects
  • Identity-matched picks: choose cast copy, choose graveyard card, choose stack target

variable length — one score per currently legal token, masked by what's actually pending

↓ concatenated ↓
Single masked softmax over both halves

Pointer targets are addressed by object identity for graveyard / stack / hand-reveal picks, or by (name, slot) for battlefield permanents — so two identically-named permanents or spells are still targeted correctly.

Stage 4

Reward Function

The reward is almost entirely win/loss. The only shaping on top is a small, capped, saturating penalty for wasting mana — applied only to the seat that ends up winning, so a losing trajectory is never worse off for having burned mana along the way.

deploy_reward_v6 — the production reward
with_dense_mana_burn_penalty(
    flat_win_loss_reward(),
    mana_burn_c=2.9, mana_burn_p=4.0,
    game_penalty_cap=1.5,
    refund_on_loss=True, mana_burn_weight=0.5,
)
Terminal band

+1.0 win · −1.0 loss or no-winner timeout · 0.0 every non-terminal step. No efficiency or sloppiness term at this level — every win scores the same, every loss scores the same.

Marginal single-pip mana-burn penalty, by turn

0.5 · hill(x, c=2.9, p=4.0) — reset every turn, only charged if this seat wins the game, capped at 1.5 total across the whole game.

Worst-case win reward is 1.0 − 1.5 = −0.5; every loss is exactly −1.0. A win always outscores any loss by at least 0.5 — the shaping term can never flip a win into looking worse than a loss.

What counts as "burn" (single-pip tagging)
Only mana-producing events that add exactly one floating symbol are tagged — a plain land or a one-mana dork like Llanowar Elves. Board-scaled abilities (Priest of Titania's count-all tap, a fully-online Tron land) are never blamed, because spending always consumes an untagged pip first. So the penalty targets genuinely avoidable waste, not correct big taps that happen to leave some unused.
Why "winner-only" and why deferred, not a terminal refund
Charging the loser too would make passive, mana-inefficient-but-safe play look better than a real attempt to win — so the penalty is deferred per-turn and only actually applied at game end if this seat won. That's not the same as computing the whole game's burn and refunding it as one lump sum at the end: under GAE, a charge written at step t lands directly in that step's advantage estimate, while a terminal-only refund would reach step t discounted by (γ·λ)^k — leaving early-game burns mostly un-refunded. Per-turn deferral keeps a losing trajectory bit-for-bit identical to one that never burned any mana.
Stage 5

PPO Training

Standard clipped-surrogate PPO, with two schedules that ramp over the first 50,000 cumulative games per deck: minibatch size grows in steps as training stabilizes, and the entropy bonus anneals down as exploration matters less.

Minibatch size — stepped ramp (in episodes)

doubles at fixed fractions of the 50,000-game horizon, capped at 16

Why minibatches are counted in episodes, and shuffled by episode
The recurrent trunk needs each episode replayed through the GRU in temporal order from a zero hidden state — so PPO's update never shuffles individual transitions, only which whole episodes land together in a minibatch.
What each logged metric means
These are the exact numbers charted per deck, per PPO update, on the Validation Stats page:
  • entropy — masked mean entropy of the action distribution over real (non-padded) steps
  • approx_kl — Schulman's k3 estimator, a non-negative post-step diagnostic (not the clipping trigger)
  • clip_fraction — share of steps where the probability ratio moved outside the clip range
  • explained_variance — how well the value head predicts returns, measured before the update
  • adv_std — raw (pre-normalization) advantage standard deviation
Stage 6

Mulligan Net

A separate, small network makes the keep/mulligan and bottoming decisions — trained with REINFORCE, not PPO, because a mulligan is one pregame decision scored by the whole game's eventual outcome: a bandit problem, not a sequential-credit-assignment one.

Reward is symmetric and game-level: +1.0 if this seat wins, −1.0 otherwise — no separate penalty for mulliganing more.

Probe hands — why evaluation needs synthetic hands
Self-play rarely draws extreme opening hands naturally (0-land or 7-land hands are just unlikely with a normal deck), so there isn't enough natural data to see how the net behaves at those land counts. The mulligan_audit validation check builds synthetic, seeded 7-card hands at every achievable land count (skipping counts a deck's list literally can't produce), runs them through the current live weights, and reports P(mulligan), its spread across variants, and decision entropy in bits at each land count — comparable across training checkpoints since the sampling is seeded.
Marked experimental in the code The mulligan loss's entropy coefficient currently sits at 1.0 (loss = policy loss + 0.5·value loss − 1.0·entropy), tuned up from a much smaller value specifically to fight entropy collapse toward "always keep." The source flags this magnitude as not yet validated on the main league loop — included here for accuracy, not as settled methodology.
Stage 7

Validation & Evaluation

Five checks run after each training chunk (roughly every 10% of a league's total_games, 50 games per pairing by default). A check that raises is logged and skipped — a bad validation run never aborts training.

CheckWhat it measuresOpponent
primary_vs_primary_round_robin Every primary-league deck vs. every other, mirrors included, greedy (argmax) play current live weights, within the same league
primary_vs_training_round_robin Full cross product, primary roster × training-league twin; also sums per-deck mana-burn totals the frozen training-league twin (see Self-Play League)
mulligan_audit Buckets the round robins' own opening-hand decisions by land count, plus a fresh seeded probe-hand pass n/a — post-hoc + synthetic hands
vs_history Live net vs. its own oldest still-active snapshot, and oldest archived one — the one check the opponent literally cannot change underneath it this deck's own frozen past self
round_robin_review Human-review only, 2 games/pairing, writes full replay logs into the webapp's Game Replay viewer current live weights

Win rate is consistently wins / games per deck or pairing side, from the engine's own game_over event; a no-winner horizon timeout is excluded from that denominator.

Where this data goes Every check's output and every metrics.jsonl line gets mirrored into this webapp as training runs, which is what powers the Validation Stats page — the metric names there (entropy, approx_kl, win_rate, keep_rate, …) are exactly the ones described on this page.
